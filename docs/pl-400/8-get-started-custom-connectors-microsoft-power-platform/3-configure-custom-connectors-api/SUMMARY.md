## Supported Authentication Schemes

| Scheme | Notes |
| --- | --- |
| No authentication | Anonymous access; use only when API allows it |
| Basic authentication | Standard Basic Auth OpenAPI spec; requires HTTPS |
| API Key | Standard API Key OpenAPI spec; requires HTTPS |
| OAuth 2.0 | Online connectors only; supports Microsoft Entra ID, GitHub, Microsoft account, and more |
| Windows authentication | On-premises data gateway connections only |

---

## Azure API Management Gateway

- Custom connectors are backed by Azure API Management infrastructure.
- API credentials/tokens are stored per-connection in a token store — never anonymous.
- Authentication is only required at connection creation; subsequent app/flow/Logic Apps use does not re-authenticate.
- On-premises APIs are accessed through the on-premises data gateway with the same connection model.

## Authentication Configuration (Security Tab)

### No Authentication
- No additional configuration required.
- Only use when the target API explicitly allows anonymous access.

### Basic Authentication
- Requires HTTPS to prevent sending unencrypted credentials.
- **Parameter label** values are display labels for the user, not actual credentials.

### API Key Authentication
- **Parameter label** — label shown to the user at connection creation.
- **Parameter name** — name of the parameter carrying the key in each request.
- **Parameter location** — `Header` or `Query`.
- Default Azure Functions template uses `code` as the parameter name sent via query string:
```http
https://functionurl.azurewebsites.net?code=user-supplied-code/
```
- Requires HTTPS to prevent unencrypted key transmission.

### OAuth 2.0 Authentication
- Available for online connectors only.
- Prebuilt identity provider templates (Microsoft Entra ID, GitHub, Microsoft account, etc.) pre-fill many required fields.
- **Generic OAuth 2.0 required parameters:**

| Parameter | Description |
| --- | --- |
| Client ID | OAuth app identifier registered with the provider |
| Client secret | Secret generated by the provider; can be revoked/reissued |
| Authorization URL | URL to sign in the user and authorize the app |
| Token URL | URL to fetch the access token after authorization |
| Refresh URL | URL to fetch a new token using a refresh token (usually same as Token URL) |
| Scope | Permissions requested from the user |

- **Redirect URL** is initially empty; becomes available after first save — must then be registered with the identity provider.
- Authorization tokens are short-lived; connector runtime handles refresh transparently.

### Windows Authentication
- Available only when **Connect via on-premises data gateway** is enabled on the General tab.
- No additional configuration fields required.
- User provides Windows credentials and selects an installed on-premises gateway at connection creation.

### Editing Authentication Configuration
- API Key and Basic Auth are part of the OpenAPI spec and can be edited in the Swagger editor.
- Other auth schemes store settings as extended connector properties — use the `paconn` CLI tool to modify them.

## Microsoft Entra ID (Azure AD) Authentication

### Why Prefer Microsoft Entra ID
- Authenticates on behalf of the calling user — users cannot access resources beyond their existing permissions.
- Target service knows the caller's identity, enabling deeper Azure AD-based authorization.
- Supports managed identities, eliminating manual credential management.

### Prerequisites
- Both the API service (e.g., Azure Functions or App Service) and the custom connector must be registered as separate apps in Azure AD.
- The connector app must be granted **delegated permissions** to the API service app.
- Users are prompted for consent at connection creation; some permissions require admin consent.

### Enabling Azure AD Authentication on the API Service
1. Open the **Authentication/Authorization** blade in Azure App Service or Azure Functions.
2. Enable **App Service Authentication**.
3. Set the default action for unauthorized access.
4. Configure and register the app in Microsoft Entra ID.

### Connector Configuration (Azure AD)
- Select **OAuth 2.0** as authentication type; set identity provider to **Microsoft Entra ID**.
- Required fields:
  - **Client id** — ID of the Azure AD app representing the connector.
  - **Secret** — Secret from the Azure AD app registration.
  - **Resource URL** — Resource identifier for the target service.
- After saving, copy the **Redirect URL** and add it to the connector's Azure AD app registration.
- Configuration is stored in `apiProperties.json`; `paconn` CLI can also update it.
- If the service uses CORS, allow-list Azure API Management domains (e.g., `azure-apim.net`).

### Full Setup Checklist
1. Register two Azure AD apps: one for the API service, one for the connector.
2. Delegate permissions — grant the connector app "on-behalf" access to the service app.
3. Define the connector with Client ID, Secret, and Resource URL.
4. Add Redirect URL to the connector's app registration.
5. Configure CORS on the service to allow Azure API Management domains if needed.

## Exercise: Connect to Microsoft Graph API via Custom Connector

### Task 1 — Create a Solution
1. Go to [Power Apps maker portal](https://make.powerapps.com).
2. Select **Solutions > + New solution**.
3. Enter **Contoso graph** for Display name, select **CDS Default Publisher**, and select **Create**.

### Task 2 — Test the API in Graph Explorer
1. Go to [Graph Explorer](https://developer.microsoft.com/graph/graph-explorer/) and sign in.
2. Set verb to **GET**, URL to `/insights/used`, and run the query.
3. If you receive a 403, go to **Modify permissions** and consent to **Sites.Read.All**.
4. Re-run the query — expect **200 OK** with values.
5. Copy the response JSON for use in the connector definition.

### Task 3 — Register Azure AD App
1. Go to [Azure Portal](https://portal.azure.com/) > **Microsoft Entra ID > App registrations > + New registration**.
2. Name: **Learn last used connector**; Platform: **Web**; Redirect URI: `https://global.consent.azure-apim.net/redirect`.
3. Add **API permissions > Microsoft Graph > Delegated**: `Sites.Read.All`, `Sites.ReadWrite.All`.
4. Create a **client secret** (90 days); copy the **Value** immediately (shown once).
5. Copy the **Application (Client) ID** from Overview.

### Task 4 — Create the Custom Connector
1. In the solution, select **+ New > Automation > Custom connector**.
2. Name: **Contoso graph**; Host: `graph.microsoft.com`; Base URL: `/v1.0`.
3. On **Security**: select **OAuth 2.0**, provider **Microsoft Entra ID**.
4. Paste Client ID and Client Secret from Task 3.
5. Set **Resource URL** to `https://graph.microsoft.com` and select **Create connector**.

### Task 5 — Add an Action
1. Select **Definition > + New action**.
2. Summary: **Last used**; Operation ID: **LastUsed**.
3. In **Request**, select **+ Import from sample**: verb **GET**, URL `/me/insights/used`.
4. Select the default response, import the Graph Explorer JSON as the response body.
5. Select **Update connector**.

### Task 6 — Test the Connector
1. Select the **Test** tab > **+ New connection** and provide credentials.
2. Select **Refresh connections**, then **Test operation**.
3. Expect a **200** response with recently used items.

## Sharing and Moving Connectors Between Environments

### Logic Apps
- Custom connectors are visible to the author and all users in the same Microsoft Entra ID tenant and Azure subscription, in the same region — no explicit sharing required.

### Standalone Connectors (Outside Solutions)
- Shared explicitly via the **Share** tab on the connector.
- Sharing levels:
  - **Organization**: Can view (use only).
  - **User/Group**: Can view + share, or Can edit.
- When sharing an app or flow that uses a connector, the connector can only be used within that app or flow.
- Deleting a shared connector deletes all associated connections — makers should be aware of dependencies.

### Connectors in Solutions
- Can be transported between environments as part of the application lifecycle.
- Connections cannot be included in solutions; use **connection references** instead.
- Connection references are created implicitly when an app or flow using the connector is added to the solution.
- On import, users are prompted to provide or create a connection for each reference.
- Access is controlled by **Dataverse role-based security** (Connector and Connection Reference tables), not by sharing.
- Scope-level privileges can restrict connectors to specific business units.

### Sharing Outside the Organization
- Certify the connector to make it publicly available.
- Make configuration files open source.
- Use a solution to transport the connector.
- Download and share configuration files directly.

> **Recommendation:** Use solutions for sharing connectors between environments or organizations for maximum flexibility and control.
